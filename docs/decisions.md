# SavePoint v2 - decisions

Choices made for the rewrite. The original v1 plan remains the behavioral spec; this file records only where v2 departs from it or fills a gap it leaves open. Each entry: the decision, then why.

## D1. Rewrite in C# / .NET 10 with Avalonia UI

The original plan fixed Electron + TypeScript. The rewrite rules out TypeScript and calls for a native desktop stack. C# on .NET 10 with Avalonia UI:

- Native desktop app, no browser runtime, small memory footprint compared to Electron.
- Cross-platform UI toolkit (Windows, macOS, Linux), which keeps the plan's "a Linux/macOS adapter later is additive" promise. WPF and WinUI are Windows-only.
- .NET covers what the TypeScript app needed npm packages for: `Process` with `Kill(entireProcessTree: true)` (replaces the hand-rolled taskkill tree kill), process enumeration (replaces ps-list), `DriveInfo` (free space), `FileVersionInfo` (exe version), `System.Text.Json` (catalog), `ArgumentList` (no shell quoting of git arguments).
- Mature test tooling (xUnit) and headless UI testing (Avalonia.Headless), including rendering screens to PNG for visual review.

## D2. Keep the git-backed engine and bundled MinGit

Unchanged from the plan: one install repo and an optional external repo per game, Profile = branch, capture = commit, restore = checkout, split git-dir/work-tree. Git runs as a subprocess against a bundled MinGit, never a system git. The engine shells out directly (no LibGit2Sharp): libgit2 is weaker on large binary trees and packfiles, which is exactly this workload, and the plan already chose real git for that reason.

## D3. No IPC layer; a service facade instead

Electron needed IPC between renderer and main. A native app does not. The plan's IPC-boundary rules still apply, moved to a service facade the UI calls: long operations run as jobs with progress events, errors are translated to catalog message ids before they reach any view, and views never touch git or the file system directly.

## D4. UI copy in an ICU MessageFormat JSON catalog

The plan requires every user-visible string to come from a catalog, with plural and select support, and a test that bans git vocabulary. v2 keeps the v1 catalog format (`en.json`, ICU MessageFormat) rather than moving to .resx, so the finished v1 copy carries over and a translator works with the same format. Formatting goes through an ICU MessageFormat library; dates and numbers through `CultureInfo`.

## D5. Solution layout

- `src/Savepoint.Core` (net10.0): domain, engine, services, platform interfaces. No UI references. OS-specific tables and calls live under `Platform/Windows`, `Platform/Linux`, `Platform/MacOS` behind interfaces, selected at runtime (see D9).
- `src/Savepoint.App` (Avalonia): views, view models, theme, localization, OS integration (dialogs, notifications).
- `tests/Savepoint.Core.Tests`, `tests/Savepoint.App.Tests` (xUnit).
- `tools/FakeGame`: a stand-in game exe for end-to-end tests (the v1 repo had the same tool).
- `build/`: MinGit fetch with SHA-256 verification, packaging scripts.

## D6. Storefront auto-fetch stays out of scope

The plan marks it "Phase 6 (stretch, later)" and "deferred until v1's manual-capture model has proven itself". v2 ships the manual-capture model complete and does not build storefront fetching.

## D7. Engine-based ignore suggestions and compression knobs stay out

The v1 background-jobs proposal floated curated per-engine ignore lists (Idea B) and object-store compression knobs (Idea C). Both were dropped during v1 dogfooding: engine caches live in AppData, outside the tracked install, and git compression gains on binary assets are marginal. The win that shipped was capture speed through git config tuning, which v2 keeps. One compression setting did come back, for speed rather than size: `pack.compression = 0` (D50).

**Logs and crash dumps (decided 2026-10-24).** The no-built-in-rules call is reversed for three extensions only. A mod loader rewrites its log on every run, so each session warned of an update and added a version-and-mods snapshot. Across the Steam and GOG installs measured on the dev PC, `.log`, `.dmp` and `.mdmp` files were always run-time output. Folder names such as crash, cache or shaderCache were not safe (shipped tools, shader caches and game data use them), and `.tmp` and `.bak` are real content in some games, so nothing else is included.

- A game has two lists of rules: `IgnorePaths` applies to both folders, and `InstallIgnorePaths` (JSON `installIgnorePaths`, absent in older definition files) applies to the game's own folder only. `GameDefinition.IgnorePathsFor(role)` gives the install folder both lists (the install-only rules first, so a later negation in the both-folders list, such as `!keep.log`, can override a default, since the last matching rule wins) and the saves folder only the first, and every exclude file, capture, preview, switch and folder-move check reads it.
- The defaults are install-only. New games (manual Add, templates, library import) start with `**/*.log`, `**/*.dmp` and `**/*.mdmp` in "Files to leave out of the game's own folder". They show and remove like any rule; a blank new game explains them in a note, templates and imported files do not. Existing games are not changed. A first design made them game-wide and dropped a rule whenever the saves folder held a match. Every file `**/*.log` matches is a log, so Unity games, which keep `Player.log` in their saves folder, lost the default entirely, and the message called the log a save. Logs in the saves folder are small and change with the saves, so they stay in snapshots.
- A game-wide rule that is one of the default strings (from a definition file or a template) is checked when a game is added (by hand or from the library), reconnected or started fresh: git itself (one `ls-files -o -i` walk with a private list, never the saved exclude file) looks at the saves folder, the index and every profile's newest point, and a rule that would name one of those files moves to the install-only list, where it is always safe. The editor, or the library dialog, says which (`gameEditor.ignorePaths.savesKept`, `library.add.line.rulesMoved`). If the check cannot run, those rules move too, a warning is logged and the message says SavePoint could not check (`savesUnchecked`, `rulesMovedUnchecked`), since adding a game must not fail. A rule the player types is kept as typed.
- After play, when every changed file in the game's own folder is a log or crash dump, the dialog says so instead of the update note and offers "Leave these out from now on". Candidate rules are picked ignoring case, then offered only if git, under the install folder's own `core.ignorecase`, names every changed file. They go into the install-only list, so they need no saves check. A file SavePoint could not read (another program holds it) is judged by its name like any other, so a held log still gets the offer and a held game file still gets the update note.
- History and the switch counts never count logs and crash dumps as mod files, for older snapshots too.

## D8. "Clear all data" is a v2 requirement

v1 listed "add a clear all data button" as an open TODO. v2 ships it in Settings behind a typed confirmation. It removes SavePoint's own storage, catalog, and consent markers, and never deletes or rolls back files in a game's install or save folders: whatever is on disk at that moment stays as it is.

## D9. v2 ships on Windows, Linux, and macOS

Decided on 2026-10-20: v2 is fully cross-platform. This replaces the plan's "Windows only for v1, seams for later". Consequences:

- Bundled git on every platform, still nothing for the user to install: GitHub Desktop's portable git builds (dugite-native: Windows, macOS x64/arm64, Linux x64/arm64), pinned by version and SHA-256. Windows can keep MinGit if dugite-native proves unsuitable there.
- Path-safety denylist tables and path tokens for all three OSes. The plan already sketches the macOS and Linux tiers; tokens map to the OS conventions (XDG dirs on Linux, `~/Library/Application Support` on macOS).
- Launch covers Windows `.exe`, Linux native binaries and scripts, macOS `.app` bundles, and storefront URIs through each OS's opener. Exe version reading uses a managed PE parser, so it also works for Windows games run through Proton on Linux.
- Notifications, single-instance, folder reveal, and OS theme detection sit behind platform interfaces with one implementation per OS.
- Copy that names the OS ("Match Windows", "a Windows folder") becomes OS-aware through ICU `select`.
- Packaging: an installer per OS (Windows installer + portable, macOS app bundle, Linux AppImage).
- Verification: Windows natively; Linux through the local WSL Ubuntu with a workspace-local .NET SDK and bundled git; macOS cannot run on this machine, so its code stays on shared POSIX paths, its tables are covered by data-driven tests, and it is flagged as unverified on real hardware.

## D11. Port Material Color Utilities instead of depending on a C# port

The MD3 palette needs HCT, `SchemeTonalSpot`, and the surface-container roles. The only C# port with those roles (Bdziam.DynamicColor 0.0.11) has had no change since April 2025 and an unclear license. v2 ports the needed subset of Google's Apache-2.0 library (with attribution) and verifies it with golden vectors generated from the official `@material/material-color-utilities` 0.3.0, the exact version v1 pinned, for all five seeds in both modes. The token table in the v1 design is a second check for the blue seed.

## D12. Static, subset fonts built from the official variable fonts

Avalonia does not render variable fonts. Roboto, Roboto Mono (OFL 1.1), and Material Symbols Rounded (Apache-2.0) ship only as variable fonts upstream. v2 instantiates static weights with fontTools and subsets Material Symbols to the icons the UI uses, at its default axes (FILL 0, wght 400, GRAD 0, opsz 24). The generator script lives in `build/fonts/`; the generated fonts and their licenses are committed. Icons are referenced by code point, not ligature.

## D13. Resolutions for v1 defects found during the inventory

Inventories of the v1 code listed behavior v1 got wrong or left undecided. v2 resolves each on purpose:

1. **Consent marker and ignore rules stay out of the game folders' history.** v2 never writes a `.gitignore` into a game's folder. The folder's rules (`ignorePaths`, plus `installIgnorePaths` for the game's own folder, D7) and the marker file name are written to `<gitDir>/info/exclude`, which lives in SavePoint's storage. The marker is therefore never committed, so checking out an older point can never rewrite it. Previews read the same exclude file and never write into the work tree.
2. **A corrupt catalog file is never overwritten.** Missing means empty; unreadable or invalid JSON raises `CatalogCorruptException`, the app shows a recovery screen naming the file, and no write happens until it is resolved. Every overwrite first copies the previous good file to `<name>.bak`.
3. **Catalog writes are serialized** through one async lock per catalog store.
4. **Sessions live for the process lifetime.** Settings changes and storage moves swap dependencies; they never rebuild the launch orchestrator or drop a running session.
5. **A running game blocks destructive operations on that game**: delete game, delete profile, storage move, and clear all data refuse with a specific message until the session ends.
6. **`versionOverride` is part of the Profile schema.**
7. **History sorts by `DateTimeOffset`**, never by string.
8. **Launch checks both folders for unsaved changes before switching either.**
9. **Profile delete validates both folders before deleting from either**, so a refused delete changes nothing.
10. **A grace for a launcher stub stays**, two minutes since 0.9.2 (it was 30 seconds, which ended a link start's session while a slow launcher was still starting the game, even with a process name set), but the running card offers "I'm done playing" from the first second, so the wait never blocks the user. The after-play dialog says how the session ended. When nothing SavePoint could see ran (a link start, or a started program that exited within the relaunch window) and the program name never showed up, it says "SavePoint didn't see the game running" instead of a play time and suggests the name may be wrong or the game slower than two minutes to start. When the started program ran past the relaunch window but the name never showed up, the session ends at that program's exit after the grace, so the play time is real, and the dialog adds a softer hint to check the name. Both offer "Open Edit game", which leaves the new changes as they are (like Not now) and opens the editor; with the after-play dialog turned off, a toast says the same once. When SavePoint could not read the list of running programs for the whole grace, the dialog says it couldn't tell how long you played and blames nothing.
11. **`exePath` must be relative to the install folder** and must not escape it (`..`). The editor's Browse converts a picked file to a relative path or refuses one outside the install folder.
12. **Process-name matching** is case-insensitive on Windows and macOS, ignores a trailing `.exe` difference, and on Linux also matches the executable's file name (the kernel truncates process names to 15 characters, which would otherwise break games run through Proton).
13. **Read-only git calls run with `GIT_OPTIONAL_LOCKS=0`**, so previews and row stats never take `index.lock` while a capture or switch runs.
14. **Duplicate and discard take the per-game lock.**
15. **Exe version reads are cached** by the blob id of the exe at that profile's tip.
16. **Free-space checks target the volume that is written**: the storage volume for captures and optimization, the game folder's volume for switches.
17. **Automatic optimization is preemptible.** It starts after a capture when a repo passes 5000 loose objects. A launch, capture, or delete on the same game cancels it (repacking is safe to interrupt) and proceeds; the next capture re-triggers it.
18. **Cancel reaches every cancellable job.** Captures (including post-play), switches, optimization, and storage moves all take the job's cancellation token. A session wait is not cancellable; "I'm done playing" ends it.
19. **Launch flow state lives above the views**, so changing screens, layouts, or the selected game never loses a running session or its post-play prompt.
20. **Partial results are judged per folder.** A job that succeeded for one folder and failed for the other is reported as partial everywhere (the "Half of that save worked" card), never as success.
21. **Every failure has visible copy.** The five message ids v1 could emit without a catalog entry get entries, and no action fails silently.
22. **Game notes survive editing.**
23. **Default storage root is a local, never-synced folder**: `%LOCALAPPDATA%\SavePoint\Storage` on Windows, `$XDG_DATA_HOME/savepoint/storage` on Linux, `~/Library/Application Support/SavePoint/Storage` on macOS. v1 used `Documents\SavePoint`, which OneDrive commonly syncs, a bad home for tens of GB of game data. First run shows the location and Settings can move it.
24. **Git never reads the user's global or system config.** Every git process runs with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` pointed at an empty file, and a fixed identity, so a user's `commit.gpgsign`, hooks path, or aliases can never change what SavePoint does.

## D14. Playing from an older point, then saving

**Replace after a normal session (decided 2026-10-24).** "Replace <snapshot> with this session" targets the newest snapshot History lists under the played profile (History's capture-id grouping and first-profile-in-catalog-order ownership; newest by date across both folders). Each folder with something unsaved is judged: where the snapshot has no commit, the unsaved files are added as a new commit (nothing is rewritten there); where it has one, that commit must be the profile's newest in the folder and reached by no other profile's branch, and is then rewritten; anything else refuses the folder. Replace is offered only when no folder refuses and at least one is rewritten, so with nothing unsaved at exit it is not offered. The same rule runs again inside the save, under the game's lock: if a folder changed after the dialog and the rule now fails, every folder is saved as a new snapshot and the result says so ("kept as new"), the only place that card appears. The rewritten and added commits all carry the session's new capture id, so the replacement is one snapshot under a new id and the old id leaves the rewritten folders. The verdict per folder is written into the save's plan when it is judged (a folder judged clean that is written before it is saved gets a plain commit, never a rewrite), and a retry of a failed save follows the first judgment instead of judging the remaining folders again. So a profile made from another, or a duplicate, never rewrites a snapshot it shares, and the profile it was made from cannot rewrite that shared snapshot either until it has a newer one of its own. Before this, a profile made with New profile was offered the other profile's snapshot by name.

**A session that changed nothing (decided 2026-10-25).** When a session that did not start from an older snapshot leaves both folders unchanged, the after-play dialog preselects Not now and makes it the main button; keeping is still offered but not recommended, since it would only add a copy of the last snapshot. Found in the Linux desktop checks, where the dialog said it found nothing to keep and still recommended keeping.

The v1 plan ("Save history within one Profile") requires two choices when the player continued from an older point and then captures: move the profile forward from that point (the newer points stop being part of the profile, recoverable until the next storage optimization) or fork a new profile from that point, with fork as the safer default. v1 never built this (it threw `detachedCaptureNotSupported`, later patched with keep-as-new in the launch dialog). v2 builds it:

- The post-play dialog, when the session started from an older point, offers: **Keep this as a new profile** (default, name field prefilled), **Continue "<profile>" from here** (moves the profile forward; second confirmation that names how many newer points leave the profile), and **Not now**.
- `SessionCompletion` variants: `CaptureNew(message)`, `UpdateExisting(message)` (amend), `ForkNewProfile(name, message)`, `MoveForward(message)`, `Skip`.
- Engine: fork = create a branch at the current (detached) commit, switch to it without touching files, commit; move forward = point the branch at the current commit (`reset --soft` semantics on the branch ref, never touching files), then commit. Both refuse unless the folder is on the commit the session started from or a descendant of it.

## D15. History points and "Go back to this"

A history point is one capture event. Each capture writes a `Savepoint-Capture: <guid>` trailer into the message of every commit it creates (one per folder), so points are grouped exactly, never by matching timestamps. The trailer is never shown.

- Point kinds (2j): **Version, mods and save** (both folders changed), **Version and mods** (install only), **Save only** (external only). The card's line ("Save only · 1.6.640 with 212 mod files") reads the install state current at that point.
- **Go back to this** opens the launch flow targeted at that point: each folder is restored to its commit for that point, or, for a folder the capture did not touch, to that profile's latest commit at or before it. A point that is not the profile's tip restores detached, and the next capture after playing follows D14 (fork by default).
- The launch dialog's save picker is the same mechanism restricted to save points of the target profile (plan step 2 and 2b).

## D16. Large incompressible files skip delta compression

Per the plan's Maintenance section, every repo gets `<gitDir>/info/attributes` (not a file in the game folder, consistent with D13.1) marking already-compressed formats `-delta`: archives (`zip 7z rar gz xz zst cab`), media (`mp4 webm mkv bik bk2 usm ogg mp3 flac`), and common game containers (`pak ucas utoc bsa ba2 archive vpk pck`), plus Unity's block-compressed containers (`bundle unity3d assetbundle resource`; see D50 for the measurement). Text and small binary files keep delta compression, and so do Unity's `assets` and `resS`, which are not block-compressed and shrank to 13 to 68% under zlib in real installs.

## D17. Deleting a profile warns about history only it holds

The plan's profile list says Delete "warns if it's the only place holding some history". v2 computes, per folder, the points reachable from that profile and from no other profile (`rev-list <branch> --not <every other profile branch>`). The delete confirmation names how many points will be lost and that their space is freed by the next storage optimization; zero means a plain confirmation.

## D18. Startup checks and recovery

On launch, before any screen: verify the bundled git (`git --version`); failure shows a dedicated error screen naming the path and what to reinstall, never a silent failure. Stale `index.lock` files under the storage root are removed once, by the first startup check and before any git work, so every lock found then predates the current process (SavePoint is single-instance and owns every git process on its own repos; see D31); during a run, a lock is removed only under the game's lock with no SavePoint git process in flight for that repo. A corrupt catalog file shows the recovery screen from D13.2.

## D19. Onboarding and editor guidance from the plan's risk table

- First run and the game editor warn against online games protected by anti-cheat (the plan's explicit non-goal), without attempting detection. The warning gives the reason, because there is no technical conflict: SavePoint never injects into a game, reads its memory, or hooks it. Anti-cheat checks the game's own files, so changed or rolled-back files can get an account flagged, and those games forbid mods, require the latest version online, and keep progress on their servers, so SavePoint cannot help them. Games that can be played offline with anti-cheat turned off for mods are fine.
- The game editor recommends turning off the storefront's cloud saves for a managed game (Steam Cloud, GOG Galaxy), next to the launch-method choice.
- Long paths: `core.longpaths=true` everywhere, and the engine's tests include a tree deeper than 260 characters on Windows.

## D20. Translator workflow

The v1 FormatJS extraction step becomes two tests plus a short guide: every key referenced from XAML or C# exists in `en.json`, `en.json` has no unreferenced keys, and every additional catalog (`<locale>.json`) has exactly the same keys with ICU arguments that match English. Adding a language is dropping a file next to `en.json`; the locale list in Settings is driven by the files present. (Refined by D39: catalogs are embedded at build time, so a language is added to the source tree and ships in a new build, and Settings shows no list until a second catalog exists.)

## D21. Licensing of the bundled git

Distributing git means shipping the GPLv2 text and a written source offer pointing at the exact upstream source tags (git-for-windows `v2.56.0.windows.2`, git `v2.53.0`, dugite-native `v2.53.0-4`). The bundle is pruned of components SavePoint never uses (Git Credential Manager and its UI assemblies, Git LFS, network helpers), which also shrinks the installer; whatever stays is listed in `THIRD-PARTY-NOTICES.md` with its license. From 0.9.5 the source archives (the three tags and every MSYS2 and MINGW package in MinGit) are published once per bundled git version as a release of their own (`git-sources-<MinGit version>`), and each app release links to it, instead of every release carrying about 55 identical archives; 0.9.2 to 0.9.4 keep theirs so their checksums still hold.

## D22. Colors come from SchemeTonalSpot; the mockup hexes are approximate

The v1 design's token table was evidently drawn with the legacy `Scheme` API (its light primary `#00639D` and light onPrimaryContainer `#001D34` match that API exactly), while v1 shipped `SchemeTonalSpot` at contrast 0, as the design itself instructs ("derive them from the theme instead", "hardcoding these hexes would break the accent-preset feature"). v2 follows v1: every role comes from `SchemeTonalSpot`. Dark mode lands within a few units of the table; light primaries are slightly less saturated. Fidelity and Content variants were checked and rejected: they match the light primary better but turn primary containers into the saturated seed color, which departs further from the mockup. Roles M3 does not define (warning, success) come from fixed-hue tonal palettes at the same tones M3 uses for error (40/100/90/10 light, 80/20/30/90 dark): warning hue from the mockup's gold `#F5D488` (the first pass used amber `#f9a825`, which read orange), success hue from green `#2e7d32`.

## D23. Api contract details settled after the contract landed

- **History count**: the History header counts capture events (D15 points), not column rows. The mockup's "9 points kept" double-counts one point that appears in both columns; the seeded data says 8.
- **Cancelled reads**: a read whose token is cancelled returns a failure with `error.operation.cancelled`; view models discard results of requests they cancelled and never show that message.
- **New profile rows**: the catalog row is written when the profile's first capture finishes with at least one folder saved. A capture that saves nothing leaves no row and no branch (fixes v1 defect 9). A partial result keeps the row and shows the "Half of that save worked" card with a retry for the missing folder.
- **Settings save**: `ISettingsApi.SaveAsync` never changes `StorageRoot` or `LastOptimizedAt`; storage moves only through `RelocateStorageAsync` and the optimized date only through optimization jobs.

## D24. Public APIs carry XML documentation; project docs ship with v2

- Every public type and member in `Savepoint.Core` has an XML doc comment (`///`): a `<summary>` stating the contract (what it promises, failure ids it can return, threading of events), plus `<param>`, `<returns>`, `<remarks>` only where they add information beyond the name. CS1591 is an error for `Savepoint.Core`. `Savepoint.App` documents its public view-model and service surface the same way; generated and view code-behind are exempt.
- The one-line rule for comments applies to inline implementation comments only; API docs are the contract and are written to be read without opening the code.
- Already-merged Core code gets a documentation pass once the in-flight branches land, then the warning is switched on.
- Project documentation (README, user guide, developer guide covering architecture, building, testing, and adding a language) is a v2 deliverable, completed with the packaging work. An API reference is generated from the XML docs.

## D25. No Git LFS; large files handled by git's own store and geometric repacking

Git LFS is pruned from the bundle on purpose. LFS solves network transfer: it keeps large files out of clones by storing them on an LFS server. SavePoint has no remote; everything is local. Locally, LFS would add a second object store with its own cleanup (`git lfs prune`), run a clean/smudge filter on every tracked file, and introduce a failure mode where a broken or missing filter leaves pointer files in the game folder instead of the game's real files. Git's own store already keeps each distinct file content once across every profile.

What LFS would have avoided is real, though: a full `git repack -a -d` rewrites every object, so on a 60 GB install each optimization would copy 60 GB. v2 therefore:
- optimizes with geometric repacking (`git repack -d --geometric=2`, both automatic and manual), which packs new objects and merges only small packs, so the large packs from the first capture are written once and left alone. Geometric repacking alone does not guarantee that: it weighs packs by how many objects they hold, so a capture's streamed pack (a few huge objects) is always the lightest and was rolled up within a few routine repacks, rewriting every big archive (measured with git 2.56; about 85 GiB for Cyberpunk on the second routine repack after the first snapshot). So every pack a capture's add writes gets a `.keep` (written atomically, text starting `SavePoint:`), which geometric repacking honors, and each routine repack first keeps any pack of at least 128 MiB that holds at most 1024 objects (read from its `.idx` header; this covers stores from before the keeps and a keep a failed write missed, while a routine-merged pack of small saves holds far more objects and stays in the geometric sequence);
- sets `core.bigFileThreshold=128m`, so files above it are streamed into the store without delta search (game binaries and archives rarely delta well) and without loading them whole into memory;
- keeps the D16 `-delta` list for compressed formats below that size.

## D26. OS integration without a Windows-specific target framework

WinRT toasts (`ToastNotificationManager`, chosen in D10) need the `net10.0-windows10.0.x` target framework, which would split every project's build by OS. v2 keeps one `net10.0` target and uses:
- **Windows notifications**: `Shell_NotifyIconW` info notifications through P/Invoke on the main window's handle. Windows 10 and 11 deliver these as toasts in the notification center under the app's name and icon. Supersedes the WinRT row in D10.
- **Linux notifications**: `org.freedesktop.Notifications.Notify` over D-Bus with `Tmds.DBus.Protocol`, which Avalonia's Linux backend already depends on; silently skipped when no notification service runs.
- **macOS notifications**: `osascript -e 'display notification ...'` (no app signing or entitlement needed).
- Notifications fire only while the window is unfocused or minimized, and only for capture, optimize, storage move, and clear-data jobs (the v1 proposal's rule), never for launches.
- **Single instance**: a named mutex per user plus a named pipe; a second launch asks the first to show and focus its window, then exits.
- **Reduced motion**: read from the OS (Windows `SPI_GETCLIENTAREAANIMATION`, macOS accessibility "reduce motion", GNOME `enable-animations`), feeding `ThemeService.ReduceMotion`.
- **Reveal in file manager**: Explorer `/select`, `open -R`, `xdg-open` on the folder.
- **Linux apps menu entry (opt-in)**: a plain AppImage has no desktop entry, so GNOME shows a generic icon. Settings offers "Add SavePoint to your apps menu" only on Linux when `APPIMAGE` names an absolute path and SavePoint itself runs from inside `APPDIR` (every program started from another AppImage inherits that AppImage's `APPIMAGE`). It writes the 256 and 512 px icons under `icons/hicolor/<size>/apps/savepoint.png`, then `$XDG_DATA_HOME/applications/savepoint.desktop` (default `~/.local/share`; `Exec` is the quoted AppImage path, `TryExec` the same path so desktops hide the entry when the file is gone, `StartupWMClass=SavePointApp`, `Categories=Utility;`, a `Comment` from the catalog, marked `X-SavePoint-Managed=true`), each through a randomly named temp file and a rename. A failed add or update leaves the previous entry as it was. An entry without the marker, or anything at that path that is not a regular file of at most 64 KB, is someone else's and is never changed or removed. An entry whose `Exec` or `TryExec` names another file, or whose icon is gone, shows as out of date with Update. Remove deletes the entry and SavePoint's icons, including icons left behind by an entry deleted by hand, and then the icon size folders Add created (recorded in the entry as `X-SavePoint-Created-Folders`) when they are empty; a folder it did not create, or one with anything else in it, stays. `update-desktop-database` runs on the user's applications folder when present; `gtk-update-icon-cache` runs only when the user already has an icon cache (otherwise the folder's time is touched), so SavePoint never leaves a cache file of its own. Failures are ignored and nothing asks for administrator rights.

## D27. The Linux gate retries failed tests up to twice, and says which

The Linux gate runs under WSL on the repository's `/mnt/f` drvfs (9p) mount, because the sources live on that drive. That mount shows rename/visibility races ordinary Linux file systems do not (a file just renamed into place is briefly "not found"), so file-heavy tests fail at random there, a different one each run. The Linux gate therefore re-runs failed tests up to twice and prints every test that needed a retry; a test failing all three times fails the gate. The Windows gate never retries, so real races in SavePoint's own logic are still caught there. Product code does not treat "file not found" as transient, since on a real file system that would hide genuine losses.

## D28. What a capture stores, and how optimization reclaims space

Findings from the engine work that change behavior the plan relies on:

- **A game folder's own `.gitignore` files are not honored.** (For a file SavePoint's patterns name that a point already recorded, D41.2 decides: a switch and a discard leave it as it is on disk, and a save stops recording it; a discard with patterns is therefore no longer one hard reset.) SavePoint must restore exactly what was on disk, so only SavePoint's exclude list (`info/exclude`: the marker and the game's `ignorePaths`) decides what is skipped. Capture lists files itself (`ls-files -z -o -m -d --exclude-from=<gitDir>/info/exclude`, never `--exclude-standard`) and stages them with `add -f --pathspec-from-file=- --pathspec-file-nul` (recorded paths that are gone, including a file a folder replaced, leave the index first through `update-index --force-remove`, because the folder's name as a pathspec would let `-f` add left-out files inside it); status/unsaved-change detection and capture previews use the same listing; clean uses `clean -fdx` with SavePoint's patterns passed as `-e`, so a file a mod's `.gitignore` names is still saved, still detected as unsaved, and still cleaned on discard.
- **Nested version-control folders are refused, not half-saved.** A folder inside the game that holds its own `.git` (a mod cloned from GitHub) would otherwise be stored as an empty pointer whose files never come back, or fail the capture outright. Capture and preview detect any nested `.git` directory or file and refuse with `error.capture.nestedRepository`, naming the folder, before staging anything. The user moves the mod's hidden history folder out and captures again.
- **Two optimization modes** (refines D25). *Routine* (`repack -d --geometric=2`) runs automatically after captures and never rewrites the large packs, which it leaves alone because they are kept (D25). *Reclaim* first removes SavePoint's keeps (any keep starting `SavePoint:` or empty; a keep anything else wrote stays), then expires reflogs, then `repack -a -d` and `prune --expire=now`, dropping everything no profile reaches: it runs when the user presses "Optimize storage" and automatically after a profile or game is deleted (preemptible like any optimization, D13.17). So D17's "freed by the next optimization" and D14's "recoverable until the next optimization" hold. Repos keep `core.logAllRefUpdates=false`; reflogs add nothing for SavePoint.
- **Profile branch names are always lowercase** (`CatalogIds`), so case-only collisions on case-insensitive file systems cannot happen.
- **Symbolic links inside game folders**: see D29 (the earlier wording here was wrong for Windows).

## D29. Engine safety rules from the engine review

An independent review of the engine reproduced three ways the engine could damage files. v2 adopts these rules, enforced in the engine itself (not only by callers):

1. **No folder links inside a tracked folder on Windows.** Git for Windows follows directory junctions and directory symlinks, so a switch or discard could delete or overwrite files outside the game folder. Capture, preview, switch, discard, and clean scan the work tree for directory reparse points (junctions, directory symlinks, mount points) and refuse with `error.capture.linkedFolder` naming the first one; nothing is staged or written. On Linux and macOS git stores symlinks as links and never follows them, so they are captured and restored as links (native games ship `.so` symlinks).
2. **A switch never runs over unsaved changes.** Non-forced checkout refuses a folder with unsaved changes (`DirtyWorkingTreeException`) instead of letting the verify/re-sync pass overwrite them; the launch flow already resolves unsaved changes first (D13.8), and this makes the guarantee hold for every caller.
3. **Clean and discard refuse a folder with no saved point** (`error.profile.noPoints`): with nothing captured, "discard" would mean deleting the whole game folder.
4. **Repo delete only deletes a SavePoint git directory**: the directory must sit inside the storage root (component-wise containment) and carry SavePoint's config stamp and git's own layout (`HEAD`, `objects/`), or the delete is refused without touching anything.

## D30. Game artwork from Steam, the name tint as fallback, the user's own image always wins

Requested on 2026-10-21: show a game's real artwork when it can be found, fall back to the existing name tint when it cannot, and always let the user set their own image. This amends the v1 design ("v1 has no art source ... Do not invent artwork"): publisher artwork served by Steam is not invented, the tint stays the fallback, and nothing is ever generated.

- **Precedence:** the user's own image; then Steam artwork for a Steam app id the user stored; then GOG Galaxy's cached artwork for the product named by the install folder's `goggame-*.info`; then Steam artwork for a detected Steam app id; then the tint. A game with none of these looks exactly as it does today. A GOG product id outranks a detected Steam id because GOG and retail builds carry other apps' ids (see the app id bullet), while an id the user typed is taken as meant.
- **Sources: Steam and GOG Galaxy's local cache, no SteamDB.** SteamDB asks not to be scraped and sits behind bot protection; its images come from Steam's CDN anyway. Other sources need an account key (SteamGridDB, IGDB) and are out of scope.
- **GOG (added 2026-10-24):** nothing in a GOG install folder is a cover (`goggame-<id>.ico` is an icon), but GOG Galaxy keeps the covers it shows on disk, so no network and no access to its database are needed. The product id comes from the install folder's `goggame-*.info` files: the most common `rootGameId`, else `gameId`, digits only. A game with DLC carries one file per product, all sharing the base game's `rootGameId` (Cyberpunk 2077 has three, and the add-on's file sorts first), and older games have no `rootGameId`. The images are `%ProgramData%\GOG.com\Galaxy\webcache\<account digits>\gog\<id>\<sha256>_glx_vertical_cover.webp` (342x482, the tall image) and `..._glx_bg_top_padding_7.webp` (1600x650, a darkened background without the title, the wide image), newest across accounts; on one PC on 2026-10-24, 927 of 930 cached products had the cover. A game Galaxy has not cached gets no GOG art. The cache is looked up on Windows only; Galaxy's folder on macOS has not been checked.
- **The Steam app id** is an optional `SteamAppId` (positive integer) on the game definition, shown and editable in the editor's Artwork section; templates may carry it. A stored id always wins. Without one, the artwork service detects an id at lookup time, in this order: a `steam://run/<id>` or `steam://rungameid/<id>` launch link; an install folder under `<library>/steamapps/common/<dir>` whose sibling `<library>/steamapps/appmanifest_<id>.acf` names `<dir>` as its `installdir` (case-insensitive on Windows and macOS); or a `steam_appid.txt` holding only digits, surrounded by any whitespace and NUL bytes, in the install folder or, failing that, a subfolder up to three levels down (shallowest first, at most 200 folders, never through a link). Detection reads files only and never writes the catalog. The manifest comes before the file because games ship files with other ids: on one PC's 174 installed games (2026-10-23), Mafia III, House Flipper, and Fallout 4 GOTY carry another app's id in `steam_appid.txt`, 13 of 25 install-folder files end in a newline and a NUL byte, and 13 games keep the file only in a subfolder such as `Binaries/Win64`, `x64`, or `bin`.
- **Two images per game, chosen by tile shape.** The wide card block uses `header.jpg` (460x215). The square tiles (rail 24, headers 34/40) use `library_600x900.jpg`, center-cropped. Both are drawn with uniform-to-fill and clipped to the tile's radius. The user's own image is one image used for every shape.
- **Where the images come from, in order:** first the Steam client's own local cache, which needs no network: `<Steam>/appcache/librarycache/<id>/` and any subfolder of it, or the older flat `<id>_header.jpg` / `<id>_library_600x900.jpg`. Newer games are cached under other names in hashed subfolders: `library_header.jpg` (460x215) for the wide image and `library_capsule.jpg` (300x450) for the tall one, and both names are accepted. On a cache of 950 apps checked on 2026-10-23, the old names alone found 720 wide and 380 tall images; with the new names, 893 and 454. The Steam folder is `HKCU\Software\Valve\Steam\SteamPath` on Windows; `~/.steam/steam`, `~/.local/share/Steam`, and the Flatpak `~/.var/app/com.valvesoftware.Steam/.local/share/Steam` on Linux; `~/Library/Application Support/Steam` on macOS. (A game with a GOG product id and no stored Steam id asks GOG Galaxy's cache first, as above, and goes to Steam only when Galaxy has nothing.) Then, only when the `LookUpArtworkOnline` setting is on (the default), Steam's CDN at `https://shared.akamai.steamstatic.com/store_item_assets/steam/apps/<id>/<file>`, falling back to `https://cdn.cloudflare.steamstatic.com/steam/apps/<id>/<file>`. Newer games are served only under a hashed path (`.../apps/<id>/<40-hex>/<file>`), and both plain addresses return 404 for them. Only then does SavePoint ask Steam's public store API, `https://api.steampowered.com/IStoreBrowseService/GetItems/v1` (no key), once per app, for the asset names, and fetch `library_capsule_2x`, else `library_capsule`, for the tall image and `header` for the wide one from `shared.akamai.steamstatic.com`. The API's answer is checked before use: its URL format must name the same app, and each asset name must be an optional 40-hex folder and a plain `.jpg` file name. Checked on 2026-10-23 against the live servers for app 3669870 (only hashed paths) and two older games (plain paths). The first version of this decision was verified on only two hand-picked games, both on the old layout, and missed the newer one.
- **Network rules:** HTTPS only; GET only; the two image hosts and the one API host above, and no redirect to any other host; a 10-second timeout; a 5 MB response cap; an `image/jpeg`, `image/png`, or `image/webp` content type (Steam serves some library images as PNG data), and the bytes must decode as an image before the file is kept. At most two requests are in flight. No cookies, and the only identifying data sent is the app id in the URL. Lookups start after the library has rendered, never before, and never delay any screen. A miss (404 or no id) is remembered with its time and retried after 7 days, or right away when the user presses "Look again" or changes the app id. These are the app's only network requests; with the setting off it makes none.
- **Storage:** images live under SavePoint's configuration folder (`<config>/artwork/<gameId>/`), not the storage root, so a storage move does not touch them. Steam's images are kept as `steam-wide.jpg` and `steam-square.jpg`, GOG's as `gog-wide.webp` and `gog-square.webp` in their own format; GOG's are dropped once Steam's are found or the install folder points at another product. Deleting a game removes its folder, and "Clear all data" removes them all. The user's own image is copied in on save, never referenced in place. It is accepted only if it decodes as PNG, JPEG, or WebP and is at most 25 MB; otherwise the editor shows `error.artwork.notAnImage` or `error.artwork.tooLarge`.
- **UI:** the tile shows the tint until the image is decoded (off the UI thread, at display size), so lists never wait or flicker. The tile stays decoration for assistive technology, since the game name is always beside it. The editor's Artwork section shows a preview, where the art came from ("From Steam", "From GOG Galaxy", "Your image", or "No artwork found"), "Choose image...", "Remove your image" when one is set, "Look again", and the optional Steam app ID field with the detected id as its hint. Settings > Appearance adds "Look up game artwork online", with a note that artwork already on this computer is used either way.
- **API:** a separate `IArtworkApi` (get, set the user's image, clear it, look again, and a change event keyed by game id). `IGamesApi` and the game summaries stay unchanged, so the fake backend, the contract tests, and the launch work do not move. Tests use a fake Steam folder and a fake HTTP handler. No test, on either gate, ever reaches the network: the backend's default is online lookup off unless a handler is supplied, and only the app's bootstrap supplies the real one.
- **Settled while building it:**
  - A read never waits: it returns what is on disk and starts any lookup in the background.
  - Steam images, including ones from the local cache, are copied into SavePoint's folder, so a Steam library change cannot take them away.
  - Any 3xx answer counts as a failure, so no redirect is ever followed.
  - The tile switches to the wide image at a width of 1.5 times its height.
  - "Look again" is disabled while the app id field is being edited.
  - When saving the artwork fails after the game itself saved, the editor stays open on the saved game and shows the error there.

## D31. Fixes from the backend and launch review

An independent review of the backend and launch code (findings BL-001 to BL-033) found two ways the merged backend could lose history or files, and several ways it could mislead the player. v2 adopts these rules:

1. **"Update existing" rewrites only the point the player named (BL-001).** A folder whose newest commit carries the named point's capture id is amended. A folder that changed but whose newest commit belongs to another point gets a new commit carrying the same capture id, so the update stays one point and no other point is ever rewritten.
2. **Ignore patterns never depend on an earlier call (BL-002).** Status, discard, clean, capture, and preview take the game's current ignore patterns from its definition on every call. Saving a game also rewrites each folder's `info/exclude` under the game lock.
3. **A missing storage folder is unreachable, not empty (BL-004).** SavePoint creates the storage folder only on first run, when no root is saved. Otherwise a missing root raises `error.storage.unreachable` everywhere the snapshot is read. A move refuses a source with no game folders while the catalog lists games, unless the source holds only the small marker file "Start with an empty folder" writes into the folder it makes (that folder is SavePoint's own and has nothing to lose; an empty folder without the marker, or one with anything else in it, stays refused), and game delete refuses while the storage is unreachable. A move scan that cannot read an entry fails the move and names the entry (BL-003).
4. **Re-pointing a folder with history is checked (BL-005).** When an edit changes the path of a folder that has saved points, SavePoint compares the new folder with that folder's newest point: how many recorded files are present at the same relative paths. When fewer than half are, the editor warns with both counts and needs an explicit confirmation. The discard confirmation names the folder and counts the files it removes and the files it restores. Discard is not refused, since bringing back deleted files is a legitimate use.
5. **Discard never runs under an open game (BL-006).** It is refused while any session for the game is open (including Exited and Completing) or the game's process is running, checked again inside the game lock. The fake backend refuses it the same way, so screen tests run against the real rule (RC-011).
6. **An unfinished switch is its own folder state (BL-007).** `FolderLaunchState` reports it together with a `LaunchTarget` the App can start. "Switch again" starts that recorded target, which completes the switch. A half-switched folder is never offered "Keep as a new profile"; Discard is always offered.
7. **A partial after-play save is retried as the same choice (BL-008).** The orchestrator and the profiles service share one `CaptureRunner`. Retrying a partial completion reruns that completion's plan for the failed folders under the original capture id, so the session still yields one point.
8. **A folder a profile never saved is left alone (BL-012).** Launching a profile that has no points in one folder (a saves folder added after the profile existed) leaves that folder as it is; the after-play capture adds it. No empty branches are seeded.
9. **One function picks the commit that stands for a point in a folder (BL-024),** shared by History and the launch resolver. A folder with no commit at or before the point is left as it is. Points are ordered by a millisecond capture time recorded in the trailer, falling back to commit order, so two captures within one second cannot be confused.
10. **A storage move deletes the old copies, and reports what it could not remove.** After the copy is verified and SavePoint has switched to the new root, the old git directories are deleted (decided; v1 left them). `StorageRelocationResult` lists the old copies left behind; the job ends Partial when the list is not empty and the App shows it. Removal ignores cancellation once the switch is done. A move writes an in-progress marker in its destination first; a later move to a folder carrying that marker is refused with copy saying an earlier move did not finish (BL-019).
11. **Closing during clear-all or a storage move asks first (BL-019).** On exit SavePoint cancels cancellable jobs and waits briefly for them, and any git it started that is still running is killed as the process ends, so no git outlives the app (an AppImage's mount stays only while a child holds it).
12. **Consent-marker game ids are validated (BL-013).** A marker whose `gameId` fails the catalog's id rule counts as corrupt, and the storage paths refuse rooted ids, separators, and dot segments, so no path from a marker can leave the storage root (on Windows, a UNC id would otherwise send the user's network login hash to a remote server).
13. **Errors keep their meaning (BL-026).** A git operation failure that is not a file in use gets its own message id and copy; a duplicate game and "no saved history to reconnect" get typed errors.

Every other finding from that review was fixed as it recommended. D18's stale-lock rule is restated to match the code: the startup sweep removes every lock once, before any git work, since each one it finds predates the process (BL-029). `UnavailableLaunchApi` and its shipped copy move to the test project, since every shipped build has the orchestrator (YAGNI-001).

## D32. Builds send no telemetry

Avalonia's packages bring in `Avalonia.BuildServices`, whose `AvaloniaStats` task sends anonymous build telemetry (machine id, hashed project and machine names, OS, tooling) from every compile, unless `AVALONIA_TELEMETRY_OPTOUT=1` is set. SavePoint is a local-first app, and its builds run on developers' machines, often by the hundred during development. `Directory.Build.targets` therefore defines an empty `AvaloniaStats` target, which replaces the package's, so no build of SavePoint sends anything whatever the environment holds. The shipped app was never affected; the package says its telemetry is build-time only. The .NET CLI's own telemetry is turned off by `DOTNET_CLI_TELEMETRY_OPTOUT=1`, which the gate scripts and the test runner script set.

## D33. Packaging with Velopack, no automatic update checks

The project calls for an installer and a portable build per OS. v2 packages with Velopack 1.2.161, the newest stable release on 2026-10-21. The `Velopack` package goes in the App, and `VelopackApp.Build().Run()` is the first call in `Main`. The `vpk` CLI is pinned as a local tool in `.config/dotnet-tools.json`, never installed globally.

- **Windows (`win-x64`):** a self-contained `dotnet publish`, then `vpk pack`, which gives `SavePoint-Setup.exe` (per-user install, Start menu shortcut, uninstall entry) and `SavePoint-Portable.zip`.
- **Linux (`linux-x64`):** the same steps on Linux (under WSL here), giving an `.AppImage`.
- **macOS:** `vpk pack` must run on macOS, and the result must be signed and notarized before anyone else can run it. Neither can be done here, so macOS packages are documented but not produced (D9).
- **Every package holds** the app, the pruned git bundle in `git/` (copied by `build/Git.targets` on publish), `THIRD-PARTY-NOTICES.md`, and `licenses/`. Each release also publishes the source archives of the git bundles it ships (D21).
- **No automatic update checks.** The app makes no network request the user did not ask for (D30's artwork lookup is the only one, behind its setting), and no release feed exists yet. Velopack contacts a feed only when the app calls `UpdateManager`, and v2 never does. A newer release installs over an older one by running its setup. An opt-in "check for updates" belongs to a later decision once a feed exists.
- **Versions:** one `Version` property in `Directory.Build.props` (semver, pre-release until the project calls it 1.0) feeds the assembly versions, the About section, and `vpk pack --packVersion`.
- **Settled while building it:**
  - **Version:** `0.9.0`.
  - **Startup order:** `VelopackApp.Build().Run()` is literally the first statement of `Main`, because vpk checks for it there and warns about a wrapper. A test reads `Main`'s IL to pin the order.
  - **vpk flags:** `--shortcuts StartMenuRoot` (no desktop shortcut), `--skip-updates`, and an `--exclude` that drops `.pdb` files and the two XML doc files.
  - **Outputs:**
    - Windows: `SavePoint-win-Setup.exe`, `SavePoint-win-Portable.zip`, `SavePointApp-<version>-full.nupkg` (vpk names it after the pack id, D38), and vpk's release index files.
    - Linux: `SavePoint.AppImage` and `SavePointApp-<version>-linux-full.nupkg`.
  - **From the final review (D41):** the commit goes into the informational version (`0.9.0+<commit>`), a tree with uncommitted changes is refused unless a trial package is asked for, the source archives' hashes are pinned in `build/git-manifest.json` (since the 0.9.0 release); the `-Sources` run checks each download against its pin before anything is published and fails on a mismatch, and a download is kept only when it matches its pin (D42), and each package's contents are listed in `artifacts/release/contents-<rid>/` and checked for the git bundle, the notices, and the license texts.
  - **Not yet covered:** the packages are unsigned, so SmartScreen warns on the setup. The MSYS2 and MINGW package sources D21 promises are published since 0.9.2 (from 0.9.5 in the bundled git's own sources release, D21): `build/msys2-sources.json` pins one source archive per package line in MinGit's `etc/package-versions.txt` (50 archives, about 670 MiB, from repo.msys2.org and Git for Windows' pacman-repo releases). A MinGit update regenerates that list with `build/msys2-sources.ps1`, which checks each archive's signature against a pinned key before taking its hash.

## D34. A local diagnostic log and a crash handler

v1's plan keeps each error's English message as dev-facing detail "for logs and a Show details toggle", and nothing in v2 writes a log yet. A failure the user reports, or a crash, would leave no trace.

- **Core logs through its own small interface,** `IDiagnosticLog` (information, warning, error, each with an optional exception). The backend takes it in `BackendOptions`, and the default writes nothing, so tests stay quiet. Core gains no logging dependency and no static state.
- **What is logged:**
  - start-up: app version, OS, the git bundle's path and version, and the result of each startup check;
  - every Api failure, at the facade: the message id, the English message, and the exception type and stack;
  - every job: start, end, status, and duration;
  - launch session changes;
  - each step of a storage move or a clear-all;
  - failed git commands: the arguments, the exit code, and the end of stderr.
  Paths appear as they are; the log never leaves the machine.
- **The App writes the files with Serilog 4.4.0 and Serilog.Sinks.File 7.0.0** (proven libraries; the rolling, size limits, and safe writes are their job). The logger is created and passed in, never the static `Log`. Files are `savepoint-<date>.log` in the platform's logs folder (`AppDirectories.LogsDir`), rolled daily and at 10 MB, with the newest 14 kept. Errors are flushed at once.
- **Unhandled exceptions** from the UI thread, the thread pool, or unobserved tasks are logged. An unobserved task exception is logged and observed. A UI-thread or domain-level crash shows a last window ("SavePoint ran into a problem and has to close") with Show details and the log folder, then exits: continuing in an unknown state could touch game folders wrongly.
- **Settings > About gets "Open the log folder".** "Clear all data" also empties the log folder, except the file in use.
- **Settled while building it:**
  - `IDiagnosticLog.CurrentFile` names the open file, so clear-all can spare it: Windows refuses to delete it, and Linux or macOS would unlink the live file. The backend wraps the log so a log that throws can never break the no-exception rule of the Api.
  - Api failures are logged once, in `ApiGuard`, with the member's name: a `SavepointException` as a warning, anything else as an error. A caller's own cancellation is not logged, because screens cancel reads on every navigation.
  - Failed git commands are warnings, since probes allow some exit codes. Each session phase logs once, not on every progress tick.
  - The Serilog sink is unbuffered, so every line reaches the disk at once.
  - On a crash, a second crash while the last window is up is only logged, and a crash with no responsive UI thread gives up on the window after 5 seconds. The exit code is 1.
  - The startup screen for a backend that failed to start names the log folder and opens it.
  - From the final review (D41): the start-up line names the commit the package was built from; a failed artwork lookup is a warning; a discard, a switch, a save that left a folder alone or skipped it, a profile delete, and a game delete each log what they did, with the paths, the bytes, and the branch tips removed; an exception thrown by an event subscriber is logged; on a crash, running jobs are asked to stop before the last window shows.

## D38. The installer's folder is never SavePoint's data folder

Velopack's Windows setup installs into `%LOCALAPPDATA%\<pack id>`, and on install and uninstall it replaces or removes that entire folder. D33 used the pack id `SavePoint`, so the setup owned `%LOCALAPPDATA%\SavePoint`. That is also where SavePoint keeps its default storage (every game's history) and its logs. Uninstalling, or installing over a copy that had already run portably, would have deleted all of it. Found while writing the dogfood checklist, before any package was installed.

- **The pack id is `SavePointApp`.** It lives in one place, `<SavepointPackId>` in `Directory.Build.props`, which both package scripts read. The setup therefore owns `%LOCALAPPDATA%\SavePointApp`, and SavePoint's data stays in `%APPDATA%\SavePoint` and `%LOCALAPPDATA%\SavePoint`.
- **Files people download keep the app's name.** The scripts rename vpk's outputs back to `SavePoint-win-Setup.exe`, `SavePoint-win-Portable.zip`, and `SavePoint.AppImage`.
- **A test pins the rule.** `PackageLocationTests` checks that no folder SavePoint keeps data in lies inside `%LOCALAPPDATA%\<pack id>`, and that both scripts take the pack id from the build properties.
- **Uninstalling keeps the user's data.** To remove that too, use "Remove all SavePoint data" before uninstalling.
- **A storage move refuses a destination inside SavePoint's own install folder,** since the next update or uninstall would delete it.

The final code review (FR-001 to FR-032, YAGNI-001 to YAGNI-006) found no critical findings and six warnings, and confirmed the engine review's fixes. It is settled as follows; everything not named here was fixed as the review recommended, or skipped with a one-line reason.

2. **Files the ignore list names (FR-002, settles a finding of the engine review; amended by D43.1).** A switch leaves every file the ignore list names exactly as it is on disk, whether or not some point recorded it, and never refuses because of one, except where a file and a folder would have to share a path (D43.1). A forced switch also protects a named file that both points record alike (found in review: it was written back over the player's copy). 3. **"Try again" after a failed check re-enters the check for the target the player chose (FR-003).** Nothing from an earlier start carries over.
4. **A storage root change gives every listed game its repositories (FR-004).** After "Start with an empty folder", and for each game a "Find the folder" target lacks, SavePoint creates the game's empty repositories at once. Games and profiles stay listed; each profile starts its history again with its next save, and the confirmation says so.
5. **Git never runs a program a repository names (FR-005).** Every git process starts with hooks pointed at an empty folder SavePoint owns and `core.fsmonitor` off, set through the environment so a repository's own config cannot override them, and SavePoint keeps only the keys `git init` writes plus its own in a repository's config. A folder adopted through "Find the folder" has its configs rewritten and its hooks folders emptied before any other git call.
6. **"Find the folder" runs the checks a storage move runs on its destination (FR-006):** the installer-owned folder (D38), an unfinished move's marker, and overlap with game folders.
7. **A left folder never forks another profile's history (FR-009).** D37.2 wins over the fork that "Keep as a new profile" would make: that folder's first point in the new profile has nothing behind it.
8. **The fallback after-play choices for an older point decide "Continue" from the recorded starts alone (FR-010),** as D37.3 does, with no folder read.
9. **Unreadable settings mean online artwork lookup is off (FR-018).** Privacy wins over art.
10. **Successful discards and deletes are logged (FR-021):** the folder or game, what was removed, and how many files, so the log can answer what SavePoint deleted.
11. **Switch progress moves while git removes files (FR-029).** The dialog's share and time left follow whichever of files and bytes is further along, so a removal-heavy switch never stands at 0%. After git writes the files, a switch or discard refreshes the index once (`git update-index -q --refresh`) before it checks every file: a file written in the same second as the index cannot be trusted by its time, and since every status SavePoint runs sets `GIT_OPTIONAL_LOCKS=0`, nothing else ever rewrote the index, so each later status, preview, dirty check and checkout read such files in full again. Measured on a 12 GB install with one 4 GB file (NVMe): removing that file went from about 42 s across the Go back preview, the launch's status read and the switch to about 2 s; writing it still reads it once, in the refresh (about 8 s for 4 GB), which is the content check D41 keeps. A file the ignore list names that differs from the target was read in full three more times (the checkout's own refresh, this refresh, and the check of every file), only to be left alone; the aligned index now marks those entries skip-worktree until the check ends, so the alignment's own reset is the one read (a 2 GB left-out cache: about 22 s to about 15 s). The mark is cleared in every outcome, and because a killed SavePoint cannot clear it, every switch, discard and save first clears any mark it finds (SavePoint never wants one at rest; a leftover would hide a change from every later save). From the end of the writes to the end of the switch, the dialog and Activity say "Making sure every file is in place" instead of showing a figure that has stopped.

## D43. Calls on the focused review of the last fix round

A focused review of the last fix round found one critical finding: a switch or a discard that writes a file where the player's disk holds a folder deletes every ignore-listed file inside it, because git treats ignored files as expendable (LR-001). It is settled as follows:

1. **A file and a folder cannot share a path, so the switch refuses rather than delete (amends D41.2).** When a switch or a discard would write a file where the work tree holds a folder that still has files the operation does not itself remove (ignore-listed or untracked), or would make a folder where the work tree holds an untracked or ignore-listed file, it refuses before it writes anything, with its own error that names the folder and the file. The player moves or deletes those files, then tries again. Silently deleting a file the player asked SavePoint to leave alone is never acceptable; leaving the profile's file unwritten would leave the install silently incomplete. The check is on the file system, not on git's rule for ignored files. A forced switch and a discard still remove plain new files inside such a folder, as they remove any new file the discard confirmation counted; they refuse over ignore-listed files and anything inside a nested repository. A switch that is not forced refuses over any new file earlier, as unsaved work.
2. **Aligning the index never loses an entry silently (LR-002).** The alignment works on a copy of the index and is compared with the original before it is swapped in; clean profile content that a named path displaces is handled under the switch journal, and any refusal puts the saved original index back as it was.
3. **"Find the folder" walks every folder of a candidate git directory for links, and every recursive walk in the engine skips links (LR-003).** A repository can gain a link after it was adopted, so the walks are link-safe on their own.
4. **A git directory cannot redirect git (LR-009).** Every git process that names a repository runs with `GIT_COMMON_DIR` set to that git directory (per call, next to `GIT_DIR`); because git still reads refs through a `commondir` file even then, every engine operation refuses a git directory that holds one, and "Find the folder" refuses a candidate whose git directory holds a `commondir` file or whose `objects/info/alternates` names a path.

## D44. Plain language, in-app help, an Activity screen, and a way back for removed snapshots

Dogfooding v2 showed that some wording was still confusing to a reader with a good grasp of git, and SavePoint's players may never have heard of version control. Banning the git words was not enough: "point", "switch", "left alone", "half switched", and "storage" still described the engine instead of what a player sees. A plain-language audit and a sweep of v1's shipped renderer (which found v1's per-game Jobs tab missing from v2) are settled as follows; the project chose items 1, 4, and 5.

1. **The vocabulary (decided: "snapshot").** The app keeps **snapshots**: a copy of a profile's game version, mods, and saves at one moment. "Save" means only the game's own save files; SavePoint's act is "take a snapshot" in status lines, "Keep" in choices, and "Create profile" in the wizard. The rest of the audit's vocabulary table is adopted as written: "new changes" (not "unsaved changes"), "Loaded now" for every in-use marker, "Go back (to this)" as the one action on any snapshot, "Replace "X" with this session", "Continue "X" from this session", "a mix of two snapshots", "not included", "snapshot folder", "Free up space", "Files to leave out", and "game settings file". This departs from the v1 spec's copy rules as the audit lists; the History title keeps "...you can go back to". Copy may gain the placeholders the audit asks for (`{ownerName}`, `{pointName}`, `{profileName}`).
2. **Permanence is stated where the choice is made.** Anything permanent says so in the option's title or its confirm button, not only in a subtitle.
3. **The profile row counts every snapshot of the profile** (not only snapshots of the saves folder), with the ownership rule History's profile filter uses, so it matches History (a duplicate that has taken no snapshot of its own reads 0), and a profile's row menu gains **Take a snapshot now**, which is also what the no-snapshot error points to.
4. **A way back for removed snapshots (decided).** Snapshots that "Continue "X" from this session" or "Replace "X" with this session" take off a profile are listed in History under **Recently removed** until the next "Free up space", and each can be brought back as a new profile. The copy says exactly that, instead of promising a recovery the app cannot do. As built: each removed snapshot is recorded before its profile moves (a record for a snapshot still on its branch is harmless and not listed), only Free up space clears the records (every Free up space, in Settings, on the Games footer, and in the library layout's game menu, asks first when it would delete some), a profile brought back and later deleted puts its snapshot back in the list until then, and a saves-only snapshot whose origin profile is gone and whose install snapshot became another profile cannot be brought back (no install to start from). A snapshot recorded in one folder only, whose other folder's commit with the same snapshot id is still held by a live profile (a Replace or Continue that changed only one folder), would fold into that profile's point in History if brought back as it is. So Bring back copies the recorded commit under a new snapshot id (same tree, parents, message, dates and empty-folders list), and one git step creates the new profile's branch at the copy and moves the record onto it. The new profile's point shows on its own, and if that profile is deleted later, the snapshot is listed again under the new id. If anything after that step fails (the other folder's branch, or saving the profile), the branches are taken back and the snapshot stays listed under the new id, and can be brought back from there. This supersedes the "recoverable until the next optimization" wording in D14 and D28.
5. **An Activity screen (decided).** A new rail item, Activity, lists running and recent jobs for the selected game, with an "All games" filter that also shows the jobs that span every game (a snapshot-folder move, clearing SavePoint's data). Each job shows what it is, which profile, its status, progress, and times; **Details** shows its output (file paths and steps in plain words, from the catalog, never git's own text), selectable for copying, following new lines unless the player scrolled up; **Cancel** stops a job that can be stopped. The Games screen's tab strip links to it, and the job status pill opens it. Launch and free-up-space jobs report steps too, so no job's details are empty. The Games screen footer gains **Free up space** for that game, as v1 had.
6. **In-app help.** A first-run tour of four steps (the profile row, Play, History, New profile) runs once after the first profile is made, can be skipped at every step, and can be shown again from Settings > Help. Six "What's this?" explanations open in place next to the ideas the audit names. A "How SavePoint works" page lives in Settings > Help (also F1 and a first-run link), ending with what cannot be undone. The three moments where the app explains itself at the point of decision are the first older-snapshot choice, a permanent discard, and the first Replace. All of it works by keyboard and screen reader, goes through the catalog (`help.json`), and stays out of an experienced player's way.
   As built: the page opens as a pane over the screen it covers, which is kept and comes back; the "seen" flags for the tour and the three decision notes live in the settings file (additive fields); the tour is marked seen when it starts, so closing the window mid-tour does not start it again, and it starts at most once per run; explanations shown inside a dialog leave out the link to the page; and Settings' theme, layout, and accent selectors no longer scroll themselves into view on open (Settings opened scrolled down and hid its title).
7. **Measuring it.** Dogfooding is the comprehension test for now; a five-player test (the audit's OQ5) is a follow-up.
8. **No em dashes (decided; replaces D39's "em dashes for asides").** Many readers take an em dash for machine-written text. An aside is a sentence of its own or a comma clause, and the catalog lint rejects an em dash anywhere. The ellipsis and the middle dot stay.

## D47. SavePoint's repositories do not trust a file's change time

The first native Linux CI run showed a preview counting a file whose content had not changed. Git compares each file's stat data with the index, including the change time (ctime) by default. A permission change, an antivirus pass, or a backup tool moves a file's ctime without editing it, so git reports the file as modified, and the preview then reads it again or, when it cannot read it, counts its whole size as new bytes.

The managed repository config sets `core.trustCtime = false` (config stamp 5, so existing repositories pick it up the next time SavePoint touches them; D50 raises it to 6). Size and modification time still catch real edits. A program that rewrites a file with the same size and then restores its old modification time would go unnoticed, which game launchers and mod managers do not do in practice.

## D48. Calls on the way to 1.0

1. **The gate runs the App and Core test modules side by side.** The one-module rule came from a machine-load problem that is gone. The App module runs one test at a time for most of its run (its UI tests share one headless UI thread), so running it beside Core uses threads that sat idle. Each module keeps 4 test threads and the gate keeps below-normal priority and the machine-wide lock. Three consecutive Windows gates passed this way with no flaky test, under the load of four implementer agents building and testing at the same time.
2. **A skip the OS's list does not name fails the gate.** A broken skip probe would turn real tests into skips while the gate still passed. The lists in `build/expected-skips/` name each test that may skip, by full name, so a new platform-specific test is a one-line edit. Lines with `~` mark timing-dependent skips. The local WSL gate has its own list, since its 9p mount cannot hold sockets or permissions.
3. **The error card never renders raw text (D44.5 holds there too).** "Show details" explains in plain words and offers "Copy details for support", which copies the exception and git's output for a bug report. Nothing technical is drawn on screen. The crash window is the one exception, decided 2026-10-24: it opens after something unexpected broke, has no error code to translate, and is what support needs, so its Show details box may show the raw text. Nothing technical shows before the player asks, and "Copy details for support" copies exactly what the box shows: the version and build, the system, where it crashed, the log folder, and the exception.
4. **Error copy knows the operation.** A held file or a full disk reads differently for a switch, a snapshot, Free up space, a snapshot-folder move and Clear all data. The App picks the operation from the job kind or the screen; an error that reaches the UI without one gets neutral copy.
5. **Storage moves and clears name folders, not git's internals.** Job lines report one line per game folder and part (game files or saves), and the left-behind cards in Settings name the game's folder.
6. **A move from an empty storage folder is allowed only from SavePoint's own empty start.** "Start with an empty folder" writes a marker into the folder it makes. A storage folder that holds only that marker can move; an empty folder without it stays refused, since it may be the wrong drive at that path (BL-004).
7. **A link start's grace is two minutes, and the editor suggests the process name.** Without a process name, SavePoint cannot tell when a game started through a link closes. When the link method is chosen and the name is empty, the editor suggests the likely game program from the install folder (launchers, anti-cheat bootstraps, redistributables, crash reporters and tools ranked down), and says why. On this machine the ranking picks a sensible program for all but two of 205 installed games. The editor's start-file list uses the same ranking (the programs the suggestion would drop follow, by depth and size), and a program the player already chose is never replaced; the list is asked for again when the game's name changes. The grace went from 30 seconds to two minutes because a slow launcher ended the session before the game appeared. The program SavePoint started never counts as the game it hands over to, even under the same name: a Steam game started directly often exits at once and has Steam start it again, which used to end the session after a second. When the started program exits within 30 seconds, SavePoint waits up to the grace for a same-named program with another process id and follows it; when it ran longer, its exit ends the session at once, so a normal quit is not held up. When the started program was itself the game and no copy follows, the session ends at that program's exit, so the wait is never counted as play time. The log names how a session ended and the process ids it followed.
8. **On Linux, a git that has exited but was never reaped counts as gone.** Both the stamp check and the wait at start read the process state from `/proc`, as the process list does, so a container whose PID 1 never reaps does not make the next start wait forever.

## D49. Switching to a profile or snapshot without playing

Before this, Play was the only way to load a profile's files, so a player who wanted the files only (to work on mods in a mod manager, copy a save, back up the folder by hand, or start the game another way) had to start the game and quit it.

1. **A switch is a launch that stops before the start.** `ILaunchApi.SwitchAsync` runs the launch's own preparation (the preview, the guards for new changes, a running game and held files) as a `JobKind.Switch` job and stops where a launch would start the game. One pipeline means a switch and a launch cannot drift apart.
2. **No session, no play time, no after-play dialog.** Nothing was played, so nothing waits for the game to exit and the last-played time stays as it was. The profile reads "Loaded now" afterwards.
3. **The game stays claimed for the whole switch job.** A launch, a second switch, a discard, a game or profile delete, a snapshot-folder move and Clear all data are refused while it runs, with their own message (`error.gameService.switching`: SavePoint is switching that game's files right now) rather than the running-game one. The claim is released on every exit path, including cancel and failure.
4. **A stopped switch recovers like a launch's.** Stopped partway through writing files, the folder is left unfinished; the next switch to the same point finishes it, and Play to another point is refused until then, as after an interrupted launch.
5. **Try again and the recovery buttons stay a switch.** "Try again", "Finish the switch" and "Review the changes" after a failed switch start another switch, never the game.
6. **A switch notifies when it finishes,** like the other long jobs. A launch does not, because the game opening is the signal; a switch has no such signal.
7. **The errors that said "Play this profile first" offer the switch.** `error.profile.notLoaded` opens a confirmation with "Switch to this profile", and `error.gameService.profileActive` offers a switch to the first other profile in the table.

## D50. Packs are written without zlib

Files above `core.bigFileThreshold` (128 MiB) stream straight into a pack, and `core.looseCompression = 0` does not cover them; `pack.compression` does. Measured on a real 85 GiB install (Cyberpunk 2077 from GOG: 5,068 files, 98.8% of the bytes in 17 archives over the threshold), a first snapshot took 35 minutes with the default compression and 9 minutes with `pack.compression = 0` (about 44 against 168 MB/s), for a store 2.4% larger (85.2 against 83.1 GiB). Two runs with the default differed by 4% in time and gave byte-identical stores. Game archives are already compressed, so zlib spends most of a large capture to save little.

The managed repository config sets `pack.compression = 0` (config stamp 6, so existing repositories pick it up the next time SavePoint touches them). Only captures write packs without zlib. The routine and reclaim repacks run with zlib at level 1 for the objects they pack anew (small save files and configs stay compressed), and they reuse data already in a pack as it is, so the big streamed archives and existing stores are not rewritten. Byte progress during a big first snapshot now tracks the bytes read more closely, since what is written is what was read. Git prints its file list through a buffered output (`GIT_FLUSH=1` does not change that for `git add -v`: 300 names arrived in the last half second of a 7 s add either way), so a watched capture stages its files under 128 MiB in batches of at most 2 GiB or 2000 files, and every file at or over 128 MiB (`core.bigFileThreshold`) in one last add. Each batch's names arrive when it ends, and a stopped batch's names are dropped, since git never finished storing them; every name becomes one detail line whatever the progress throttling drops. Details shows the newest 200 lines and a job keeps its newest 20,000 for Copy (about 3 MB; a first snapshot of Cyberpunk 2077 writes about 5,200). During the last add, "Still copying <file>: X of Y" names the big file by matching the bytes stored so far against the big files in the order git takes them (files it already tracks first, in index order, then new files by path), so the name is an estimate. Git writes one pack per add for the files it streams, and the geometric repack weighs packs by how many objects they hold, so one pack per big file would be merged by the first routine repack and every big archive rewritten; with all big files in one add, a capture writes one pack, and its keep (D25) holds it in place through every routine repack. Measured on 5.5 GB of mixed files, the batches cost 1 to 5% over one add (about 0.3 s per extra git start); an unwatched capture is still one add, and the snapshot is the same tree either way. Before each batch, files that are gone and were never recorded are dropped from it, so a temporary file a launcher deletes mid-capture does not fail the snapshot. A capture that stops after some batches leaves them staged; the next one finishes the rest, and its count includes what was already staged. Git says nothing while it closes the last pack and writes the index, so once the store holds at least 99% of the bytes and has not grown for 8 seconds (longer than git takes to hash a 128 MiB file before writing it), the progress text says SavePoint is making sure everything is stored safely instead of showing a figure that has stopped (`common.progress.finishing`). Known limit: a game whose files repeat more than about 1% of their bytes stores less than it reads, never reaches that mark, and keeps the old figure until the end. Known cost: a game with large uncompressed assets (raw audio or textures over 128 MiB) stores them at full size; no such game has been measured yet.

The first routine repack after a big first snapshot then spent most of its time on game archives that gain nothing from it. Measured on a real 21.5 GB Unity install (7 Days to Die: 18,090 files, 285 bundles holding 14 GB; `repack -d --geometric=2` over 11.7 GB of loose objects with 4 pack threads, on NVMe), the first snapshot took 200 s and the repack 570 s. Delta search over the bundles took about 240 s of that: Unity's bundles are compressed in blocks and shrank only 1 to 7% under zlib, so D16's `-delta` list gained Unity's block-compressed containers. Zlib's default level cost about 100 s more than level 1; level 0 saved another 170 s but stored the compressible small files raw and made the store 14% larger (20.3 against 17.8 GB). So the routine and reclaim repacks run at `pack.compression = 1`: the repack took 316 s instead of 570 s, for a store 1% larger (17.45 against 17.25 GB). Data already in a pack is still copied as it is, so existing stores and update rollback are untouched, and the attributes file is rewritten with every write, so existing stores take the new list at their next snapshot. `.raw` heightmaps and `.wav` audio stay delta-searched: delta saved 330 MB on the heightmaps for about 60 s. The reclaim repack at level 1 was not measured separately.

## D51. Snapshots keep empty folders

A real install (Cyberpunk 2077) ships an empty `archive\pc\mod` folder that mod tools expect. After a profile put a file in it and a switch went back, the folder was gone: git tracks files only and prunes a folder it empties. Every file matched afterwards; only the folder was lost.

1. **The list travels in the commit.** Each snapshot's commit message carries a `Savepoint-Empty-Folders:` trailer, a one-line JSON array of its innermost empty folders (their parents come back with them). Being part of the commit object, it follows the snapshot through every history operation SavePoint has (Recently removed, Bring back, keep as a new profile, Free up space, a snapshot-folder move) with no extra step. A git note was rejected because it needs its own ref and a copy whenever SavePoint makes a new commit from an old one; a tree entry would either be written into the game folder (D13.1 forbids anything but the game's own files) or be pruned as unreachable.
2. **Nothing but the folders themselves goes into the game folder.** No placeholder files.
3. **Restoring only creates.** A switch, go back, forced switch, finishing a stopped switch, discard and clean create each listed folder that is missing, skipping a folder the exclude list names, one under a link, and one where a file stands. A switch does not remove an empty folder the target lacks (git's own pruning stays as it was); discard and clean still remove empty folders the point does not hold, as before.
4. **The list honors SavePoint's excludes only.** It is filtered through `info/exclude` with a work tree set inside the git directory, so a `.gitignore` in the game folder cannot add to or negate it. Folders under links, inside nested repositories, or with unsafe names are never listed.
5. **Older snapshots have no list** and behave exactly as before.

Known limit: a change that only adds or removes an empty folder is not a change to git, so it does not make a new snapshot and the list keeps the folders as they were at the last real change.

## D52. Adding many games at once from the Steam and GOG libraries

A player with a large library added games one at a time. "Add games from your libraries" scans what is installed and adds a ticked set in one go.

1. **What is scanned.** Steam: `libraryfolders.vdf` and each `appmanifest_*.acf`, a game counting as installed when `steamapps/common/<installdir>` exists (a manifest of an installed game can carry update states). Steam's own tools (Proton, the Linux runtime, redistributables, SteamVR) are left out. Steam installed through Flatpak or Snap and on macOS is found too. GOG Galaxy (Windows): its install records in the registry, add-ons dropped. An install path that is not fully qualified, an `installdir` with separators, dot segments or a trailing dot or space, and any folder that holds another installed game's folder are left out. Apps that share one folder are listed once, under the app a template describes, else the lowest app id. Programs that are not games (benchmarks, editors) still show, since Steam does not mark them.
2. **Matching a template.** Store id first (Steam app id, GOG id), then the install folder name, ignoring case. Templates carry these in an optional `libraryHints` block (`steamAppIds`, `steamInstallDirs`, `gogIds`, `gogFolders`, and `savesByOs` per system) that never reaches a stored game.
3. **What is added.** Every add goes through the single add's checks (validation, path safety, overlap). The player confirms once, with every game's folders named. Only the install folder and the saves folder the scan showed as existing are added; a saves folder that appears later, or a template folder that does not exist yet, is left out and named in the result, and the game is added with its install folder. A template's program is used only on Windows and only when it is in the install folder; otherwise the store link starts the game, and a game started through a link with no process name from its template gets one suggested from its install folder (D48.7).
4. **"Already added"** means the install folder overlaps a game's install folder, a saves folder another game tracks, or the same Steam app id (a GOG copy is never judged by a template's Steam id). A second install of the same Steam app cannot be added.
5. **A loop, not a job.** The UI adds the games one by one through the Api, with per-game progress and "Stop after this game". It is not a job, so Activity does not list it, but quitting while it runs asks first and stops after the current game. One game's failure is reported for that game and does not stop the rest.
6. **GOG Galaxy's own folders are protected** like Steam's (D40): Galaxy's program folder and its default `Games` folder are refused as a game folder; games inside the `Games` folder are accepted.
7. **Reading the stores does not hold the storage lock,** so a scan of slow or missing drives never blocks a snapshot-folder move; the scan can be canceled and stops when its dialog closes.

## D53. Templates for many games

SavePoint shipped one template. It now ships templates for about 320 games: the games installed on the test machine and widely played PC games, each from researched facts with a source (PCGamingWiki, the store's manifests, folders seen on a real machine). Templates are discovered from the embedded resources, so adding one is adding a JSON file.

1. **A wrong saves path is worse than none.** A template carries a saves folder only when a source names it and SavePoint has a token for it. Saves under a per-user id, in Steam's userdata folder, inside the install folder, or with several candidate folders get no saves folder and a plain note saying why, so the player picks it. Every template is checked by tests: it loads, its ids and store folders are safe, every saves path resolves through the real tokens on its system and is not a file or one of the broad folders (Documents, AppData, the home folder), and no path names another game's folder.
2. **Linux and macOS use only their own entries.** A draft on Linux or macOS takes the saves folder from that system's `savesByOs` entry and otherwise leaves it blank; a Windows path does not carry over, since games under Proton save inside their prefix and native ports elsewhere.
3. **The template picker searches.** Each typed word must start a word of the game's name, ignoring case and punctuation.
4. **Every template is checked against its wiki page.** Each was matched to its PCGamingWiki page through its Steam app id, and its saves folder compared with the page's save rows, including the Steam-specific row: where a Steam copy saves in Steam's userdata folder, the template leaves the folder blank. At release 152 templates carry a saves folder, each matching its page; 168 leave it to the player.
5. **Known limit:** template notes are English text stored with the game but shown on no screen; if a screen ever shows them, they move into the catalog as note keys.

## D54. Which game version SavePoint shows

The version on a profile comes from the start program's version resource. Reading the product string first showed engine build ids as versions: Grounded read `++Game+release.1.4.7-CL-196638`. Checked on 2026-10-24 against 252 game programs on one PC (Steam and GOG):

1. **Unreal build ids** (a string starting with `++` or holding `-CL-<digits>`) give only a dotted number of three or four parts found inside them (Grounded 1.4.7, Borderlands 4 1.11.0.0), or nothing. Two-part numbers like `Release-4.26` are the engine's.
2. **Engine versions are not game versions.** Unity players (a "Unity Version" string, or a product version like `2022.3.62f2 (<hash>)`), a program whose product name is "Unreal Engine", and the fixed numeric version of Epic Games or Unreal executables (it carries the engine version, 4.27.2.0 or 5.6.1.0) show no version.
3. **Placeholders** (`1.0.0.0`, `1.0.0`, `1.0`) and strings without a digit (`^VersionString^`) are no version; a rejected product string falls through to the file string. The fixed numeric version is used only when the program has no version string at all. A game that really calls itself 1.0 shows nothing; the player can type the version on the profile.
